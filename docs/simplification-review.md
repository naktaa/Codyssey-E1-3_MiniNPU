# Mini NPU 구현 단순화 검토안

이 문서는 현재 구현을 미션 요구사항 중심의 간결한 코드로 다듬기 전에 검토하기 위한 의사결정 자료다. 아직 아래 변경을 코드에 적용하지 않았으며, 강의장에서 항목별로 유지·수정 여부를 결정한 뒤 한 단계씩 구현한다.

## 1. 검토 목적

현재 프로그램은 미션 필수 기능과 두 보너스를 모두 구현했다. 핵심 MAC 계산은 단순하지만, 기능을 확장하고 성능 측정을 보완하는 과정에서 미션 설명에 꼭 필요하지 않은 구조가 일부 추가됐다.

이번 단순화의 기준은 다음과 같다.

- 미션 원문의 필수 요구사항과 선택한 보너스 기능은 유지한다.
- 실행 결과를 이해하려면 별도의 숨은 규칙이 필요한 구조를 줄인다.
- 함수는 역할이 분명하거나 중복을 줄일 때만 분리한다.
- 초급 학습자가 코드의 핵심 흐름을 바로 따라갈 수 있게 한다.
- 이미 확보한 실행 증거와 추가 실험은 삭제하지 않고 공식 결과와 구분한다.
- 한 번에 모두 바꾸지 않고, 동작에 영향을 주는 항목부터 단계별로 수정하고 사용자 실행으로 확인한다.

목표 흐름은 다음과 같다.

```text
입력을 검증한다.
→ 같은 위치의 값을 곱하고 더한다.
→ epsilon으로 Cross/X/UNDECIDED를 판정한다.
→ JSON expected와 비교한다.
→ 고정 입력으로 순수 MAC을 10회 측정한다.
→ 보너스로 1차원 방식과 생성 필터를 별도로 비교한다.
```

## 2. 단순화 우선순위 요약

| 순서 | 검토 항목 | 필요한 이유 | 권장 방향 | 영향 |
|---:|---|---|---|---|
| 1 | 공식 성능 입력과 `matrix_store` 분리 | 메뉴 실행 순서가 공식 측정 입력에 영향을 줌 | 필수 네 크기는 고정 입력, 생성 크기는 추가 결과로 분리 | 동작·출력 변경 |
| 2 | 사용자 N×N 모드의 JSON 탐색 제거 | 저장·JSON·자동 생성 흐름이 한 기능에 섞임 | 메뉴 3에서 생성하고 메뉴 1에서 저장 필터 재사용 | 동작·출력 변경 |
| 3 | 공식 성능표에서 CV 제거 | 미션 핵심보다 통계 설명 부담이 큼 | 평균·표준편차·N²·반복 횟수만 유지 | 출력 변경 |
| 4 | README 묶음 벤치마크 축약 | 추가 실험이 공식 미션보다 큰 비중을 차지함 | 코드는 보존하고 README는 요점과 증거 링크만 유지 | 문서 변경 |
| 5 | 중복 점수 검증과 복잡한 타입 힌트 정리 | 실제 로직보다 방어 코드와 타입 표현이 어렵게 보임 | 실행 경로의 사전 검증을 믿고 간단한 타입만 유지 | 내부 코드 변경 |

1번은 결과 재현성과 관련되어 가장 우선한다. 2번은 보너스 생성기 흐름을 명확하게 만들기 위한 변경이다. 3~5번은 미션을 더 쉽게 설명하기 위한 선택적 정리다.

## 3. 우선순위 1: 공식 성능 입력과 `matrix_store` 분리

### 현재 구조

프로그램 시작 시 [`src/menu.py`](../src/menu.py)에서 실행 중 저장소인 `matrix_store`를 하나 만들고 메뉴 1·2·3에 공유한다.

```text
프로그램 시작
→ matrix_store 생성
→ 메뉴 1·2·3이 같은 저장소 공유
```

저장소에는 다음 값이 들어갈 수 있다.

- 메뉴 1에서 사용자가 입력한 필터와 패턴
- 메뉴 2에서 읽은 JSON 필터와 패턴
- 메뉴 3에서 생성한 Cross/X 필터

현재 [`src/performance.py`](../src/performance.py)는 필수 크기와 저장소의 크기를 합쳐 측정 대상을 만든다.

```python
sizes = sorted(set(REQUIRED_SIZES) | set(matrix_store))
```

측정할 크기가 저장소에 있으면 JSON의 기본 입력보다 저장된 입력을 먼저 사용한다.

```python
if size in matrix_store:
    stored = matrix_store[size]
    return stored["pattern"], stored["filters"][LABEL_CROSS]
```

### 왜 단순화가 필요한가

공식 성능 입력이 프로그램의 이전 메뉴 사용 여부에 따라 달라진다.

```text
실행 A
메뉴 2를 바로 선택
→ 3×3 기준 행렬과 JSON의 5×5·13×13·25×25 입력 사용

실행 B
메뉴 3에서 5×5 생성
→ 메뉴 2 선택
→ 생성한 5×5 입력이 공식 5×5 측정에 사용됨
```

N² 연산 수는 같아도 실제 행렬과 객체가 달라진다. 그래서 현재 README에는 공식 결과를 재현할 때 새 프로세스에서 메뉴 2를 먼저 선택하라는 별도 규칙이 있다.

이 구조의 문제는 다음과 같다.

- 같은 메뉴 2가 실행 순서에 따라 다른 입력을 측정한다.
- 평가자가 결과 재현 조건을 추가로 이해해야 한다.
- 필터 생성기 보너스가 공식 필수 성능에 영향을 준다.
- 성능값 차이가 코드 변경 때문인지 입력 변경 때문인지 구분하기 어렵다.

미션 원문은 필수 네 크기의 성능 분석과 생성 결과 재사용을 요구하지만, 생성한 값이 공식 기본 입력을 덮어쓰도록 요구하지는 않는다.

### 권장 단순화

필수 성능과 생성 필터 성능의 입력 선택을 구분한다.

#### 공식 필수 성능

항상 같은 네 크기와 같은 입력을 사용한다.

```text
3×3
→ 코드 내부 기준 행렬

5×5·13×13·25×25
→ data.json의 크기별 첫 정상 케이스
```

공식 측정 함수는 `matrix_store`를 기준 입력 선택에 사용하지 않는다.

```python
measure_size_performance(pattern_cases)
measure_1d_performance(pattern_cases)
```

#### 생성 필터 성능

보너스 요구사항인 생성 결과의 성능 분석 재사용은 별도로 유지한다.

가장 간단한 규칙은 다음과 같다.

```text
필수 크기 3·5·13·25
→ 항상 공식 기준 입력 사용

필수 크기에 없는 실행 중 생성 크기
→ matrix_store 입력으로 추가 측정
```

예를 들어 5×5와 7×7을 생성했다면 다음과 같이 처리한다.

- 공식 5×5는 JSON 기준 입력을 그대로 사용한다.
- 생성 5×5는 사용자 모드에서 재사용할 수 있지만 공식 성능 입력을 덮어쓰지 않는다.
- 7×7은 생성 필터 성능 결과에 추가한다.

표는 다음 두 가지 중 하나로 구성할 수 있다.

1. 공식 성능표와 생성 필터 성능표를 별도로 출력한다.
2. 하나의 표를 사용하되 필수 네 크기에는 고정 입력, 그 외 크기에만 저장 입력을 사용한다.

설명 명확성을 우선하면 첫 번째 방식이 좋고, 출력 간결성을 우선하면 두 번째 방식이 좋다. 어느 방식을 선택하더라도 필수 네 크기를 저장소가 덮어쓰지 않는 규칙은 동일하다.

### 단순화 후 설명

> 공식 성능은 항상 같은 네 크기와 같은 입력을 사용합니다. 메뉴 3에서 만든 추가 크기는 보너스 성능 항목으로 별도 측정합니다.

### 유지되는 요구사항

- 3×3·5×5·13×13·25×25 성능 분석
- 각 크기 최소 10회 측정
- 평균 시간과 N² 출력
- 1차원 보너스의 같은 입력·같은 반복 조건 비교
- 생성 결과의 성능 분석 재사용

### 예상 수정 파일

- `src/performance.py`: 필수 입력과 생성 입력 선택 분리
- `src/json_mode.py`: 공식 결과와 생성 결과 전달 방식 정리
- `src/report.py`: 필요하면 생성 성능 제목 분리
- `README.md`: “메뉴 2를 먼저 실행”해야 한다는 재현 조건 제거
- 관련 학습·진행 문서와 새 실행 증거

### 검토 결정

- [ ] 권장안대로 수정
- [ ] 하나의 표에서 필수·추가 크기만 구분
- [ ] 현재 구조 유지

## 4. 우선순위 2: 사용자 N×N 모드의 JSON 탐색과 자동 대체 제거

### 현재 구조

사용자 입력 모드는 다음 두 입력 방식을 제공한다.

```text
1. 3×3 필터 두 개와 패턴 직접 입력
2. 크기 선택 후 저장 또는 자동 생성 필터 사용
```

2번에서 해당 크기가 `matrix_store`에 없으면 [`src/manual_mode.py`](../src/manual_mode.py)의 `_load_or_generate_filters()`가 다음 순서로 처리한다.

```text
matrix_store에 필터가 있는가?
  ├─ 있음 → 저장 필터 사용
  └─ 없음
       → data.json에서 같은 크기 필터 탐색
            ├─ 정상적으로 찾음 → JSON 필터 사용
            └─ 파일·데이터 오류 → Cross/X 필터 자동 생성
```

### 왜 단순화가 필요한가

한 사용자 기능에 세 가지 책임이 섞여 있다.

1. 실행 중 저장 필터 조회
2. `data.json` 필터 조회와 검증
3. 필터 자동 생성

현재 예외 처리는 다음 상황들을 모두 자동 생성으로 대체한다.

- `data.json` 파일이 없음
- JSON 문법 또는 UTF-8 문제가 있음
- 해당 크기 필터가 없음
- 필터 행렬 크기가 잘못됨
- 필터 라벨이 잘못됨

따라서 JSON의 필터가 손상돼도 사용자에게 데이터 오류를 알리지 않고 새 필터를 생성해 계속할 수 있다. 프로그램은 동작하지만 원래 데이터 문제가 가려진다.

동료평가에서 설명해야 하는 흐름도 길어진다.

> 실행 중 저장소를 먼저 확인하고, 없으면 JSON을 읽고, 해당 크기의 필터가 있으면 정규화해서 사용하며, 파일이나 구조에 문제가 있으면 자동 생성합니다.

미션 보너스의 핵심은 더 단순하다.

```text
필터를 생성한다.
→ 실행 중 저장한다.
→ 사용자 모드와 성능 분석에서 재사용한다.
```

### 권장 단순화

메뉴 3을 필터 생성의 명확한 진입점으로 둔다.

```text
메뉴 3
→ N 입력
→ Cross/X 필터 생성
→ matrix_store에 저장

메뉴 1의 N×N 방식
→ 저장소에 해당 크기가 있으면 사용
→ 없으면 메뉴 3에서 먼저 생성하라고 안내
```

예상 코드는 다음처럼 단순해진다.

```python
if size not in matrix_store:
    print(f"{size}x{size} 필터가 없습니다.")
    print("메뉴 3에서 필터를 먼저 생성하세요.")
    return
```

사용자 모드에서 다음 의존성도 제거할 수 있다.

- `DataLoadError`
- `DataValidationError`
- `get_filter_pair()`
- `load_data()`
- `generate_filter_pair()` 직접 호출

사용자 모드의 역할은 다음 네 단계로 줄어든다.

```text
저장된 필터 선택
→ 패턴 입력
→ MAC 계산과 판정
→ 성능 출력
```

### 자동 생성 기능은 없어지는가

아니다. 메뉴 3의 생성 기능은 그대로 유지한다. 제거하는 것은 메뉴 1에서 저장 필터가 없을 때 JSON을 찾거나 사용자에게 알리지 않고 자동 생성하는 동작이다.

시연 흐름도 분명해진다.

```text
메뉴 3에서 7×7 생성
→ 메뉴 1에서 7×7 저장 필터 사용
→ 사용자 패턴 판정
→ 메뉴 2에서 생성 7×7 성능 확인
```

### 대안

사용 편의를 위해 메뉴 1의 자동 생성을 유지하고 싶다면 JSON 조회만 제거할 수 있다.

```text
저장 필터 있음 → 저장 필터 사용
저장 필터 없음 → 즉시 Cross/X 생성
```

이 방식도 현재보다 단순하지만, 메뉴 3에서 생성한 결과를 메뉴 1에서 재사용한다는 보너스 흐름은 덜 분명해진다. 동료평가 설명을 우선하면 “먼저 메뉴 3에서 생성” 방식을 권장한다.

### 유지되는 요구사항

- 기본 3×3 직접 입력
- N×N Cross/X 필터 생성
- 생성 결과의 사용자 모드 재사용
- 생성 결과의 성능 분석 재사용
- 실행 종료 시 저장 데이터 제거

### 예상 수정 파일

- `src/manual_mode.py`: JSON 로더와 자동 대체 제거, 저장 필터 부재 안내
- `README.md`: 사용자 모드와 생성기 사용 순서 수정
- 기존 자동 생성 로그는 과거 방식으로 구분
- 변경 후 생성·재사용 실행 증거 재수집

### 검토 결정

- [ ] 메뉴 3에서 먼저 생성하도록 수정
- [ ] JSON 조회만 제거하고 메뉴 1 자동 생성 유지
- [ ] 현재 구조 유지

## 5. 우선순위 3: 공식 성능표에서 CV 제거

### 현재 구조

공식 성능표는 다음 열을 출력한다.

```text
크기 | 평균 시간 | 표준편차 | CV | N² 연산 수 | 반복 횟수
```

미션 원문이 필수로 요구하는 내용은 다음과 같다.

- 크기(N×N)
- 평균 시간(ms)
- 연산 횟수(N²)
- 크기별 최소 10회 반복 측정

표준편차와 CV는 최소 요구를 넘어선 추가 통계다.

### 표준편차와 CV의 차이

표준편차는 측정값이 평균에서 얼마나 떨어져 있는지를 시간 단위 그대로 나타낸다.

```text
평균: 0.200 ms
표준편차: 0.010 ms
```

CV는 표준편차가 평균의 몇 퍼센트인지 나타낸다.

```text
CV = 표준편차 ÷ 평균 × 100
   = 0.010 ÷ 0.200 × 100
   = 5%
```

### 왜 단순화가 필요한가

CV 자체는 잘못된 통계가 아니다. 평균 크기가 다른 항목 사이의 상대 변동을 비교할 때 유용하다. 하지만 이번 미션의 핵심은 다음이다.

- N×N MAC 원리
- 크기별 10회 평균 시간
- N² 연산량
- O(N²) 설명

CV를 공식 표에 넣으면 다음 내용까지 설명해야 한다.

- 표준편차와 CV의 차이
- 평균이 매우 작을 때 CV가 민감해지는 이유
- 공식 개별 호출 CV와 묶음별 호출당 평균 CV가 다른 이유
- CV가 낮아도 실제 MAC 호출 자체가 안정됐다고 단정할 수 없는 이유

결과적으로 MAC과 시간 복잡도 미션보다 통계 실험의 비중이 커질 수 있다.

### 권장 단순화

공식 표에서는 CV만 제거한다.

```text
크기 | 평균 시간(ms) | 표준편차(ms) | N² 연산 수 | 반복 횟수
```

표준편차는 유지하는 것을 권장한다.

- 이미 10회를 독립 측정한다.
- 실행 시간의 흔들림을 정직하게 보여준다.
- `statistics.pstdev()` 한 줄로 계산할 수 있다.
- 평균값 하나만 제시하는 것보다 측정 결과를 이해하기 좋다.

미션 최소 기준만 맞춘다면 표준편차도 제거할 수 있지만, 현재 정한 10회 평균·표준편차 분석 방향과 실행 기록을 고려하면 CV만 제거하는 편이 균형이 좋다.

### 코드 변화

[`src/performance.py`](../src/performance.py)의 `PerformanceResult`에서 다음 property를 제거할 수 있다.

```python
@property
def coefficient_of_variation(self):
    if self.average_time_ms == 0.0:
        return 0.0
    return self.standard_deviation_ms / self.average_time_ms * 100.0
```

[`src/report.py`](../src/report.py)의 표 헤더와 행 출력에서도 CV 열을 제거한다.

### 비공식 묶음 실험 처리

두 가지 선택지가 있다.

1. 묶음 실험에서만 CV를 직접 계산해 출력한다.
2. 묶음 실험도 평균과 표준편차만 유지한다.

핵심 코드 단순화를 우선하면 두 번째 방식이 가장 쉽다. 기존 증거 문서의 CV 값은 그 당시 실제 실험 결과로 보존할 수 있지만, 새 공식 기능이나 새 표에서 계속 계산할 필요는 없다.

### 유지되는 요구사항

- 크기별 최소 10회 측정
- 평균 시간 출력
- N² 연산 수 출력
- 실제 측정 변동을 보여주는 표준편차
- O(N²) 분석

## 7. 우선순위 5: 중복 점수 검증과 복잡한 타입 힌트 정리

이 항목은 실행 중 중복되는 방어적 검증과 코드의 핵심보다 어렵게 보이는 타입 표현을 각각 검토한다.

### 7.1 `_validated_number()` 단순화

#### 현재 구조

[`classify_scores()`](../src/mini_npu.py)는 MAC 점수를 비교하기 전에 다음 처리를 한다.

```python
cross = _validated_number(score_cross, "score_cross")
x_score = _validated_number(score_x, "score_x")
epsilon_value = _validated_number(epsilon, "epsilon")
```

`_validated_number()`는 다음을 확인한다.

- `Real` 타입인가
- `bool`이 아닌가
- 유한한 값인가
- `float`로 변환할 수 있는가

하지만 공개 실행 경로는 이미 다음과 같이 입력을 검증한다.

```text
사용자 입력
→ float 변환과 NaN·무한대 거부
→ calculate_mac()
→ classify_scores()

JSON 입력
→ 숫자·정사각형·유한 값 검증
→ calculate_mac()
→ classify_scores()
```

정상 경로에서 두 점수는 이미 유한한 숫자이므로 판정 함수가 같은 성격의 검증을 반복한다.

#### 권장 단순화

판정 함수는 epsilon 정책만 담당한다.

```python
def classify_scores(score_cross, score_x, epsilon=DEFAULT_EPSILON):
    if epsilon <= 0:
        raise ValueError("epsilon must be greater than zero.")

    if abs(score_cross - score_x) < epsilon:
        return LABEL_UNDECIDED
    if score_cross > score_x:
        return LABEL_CROSS
    return LABEL_X
```

epsilon을 인자로 유지하면 미션의 허용오차 정책을 코드에서 명확히 볼 수 있다. `_validated_number()`는 제거할 수 있다.

#### 잃는 부분

누군가 내부 실행 경로를 거치지 않고 다음처럼 직접 호출하면 기존 코드가 더 친절한 오류를 냈다.

```python
classify_scores("abc", 1.0)
classify_scores(float("nan"), 1.0)
```

단순화 후에는 Python 기본 오류가 발생하거나 예상하지 못한 비교 결과가 나올 수 있다. 하지만 이 프로젝트는 외부 사용자를 위한 라이브러리가 아니라 입력 경로가 정해진 콘솔 애플리케이션이다. 실제 실행 경로에서 사전 검증하므로 중복 방어의 효과보다 설명 부담이 크다고 볼 수 있다.

### 7.2 복잡한 타입 힌트 정리

현재 코드에는 다음 타입 표현이 사용된다.

```python
Sequence[Sequence[Real]]
Mapping[str, Any]
Tuple[Sequence[Sequence[float]], Sequence[Sequence[float]]]
Dict[int, Dict[str, Any]]
```

이 표현들은 다양한 자료형을 정확하게 허용하지만, 초급 학습자가 코드를 읽을 때 실제 MAC과 JSON 흐름보다 타입 문법이 먼저 눈에 들어올 수 있다.

예를 들어 현재 MAC 함수 선언은 다음과 같다.

```python
def calculate_mac(
    pattern: Sequence[Sequence[Real]],
    filter_matrix: Sequence[Sequence[Real]],
) -> float:
```

실제 핵심은 두 행렬을 받아 점수를 반환한다는 것이다. 다음처럼 복잡한 매개변수 타입을 생략해도 프로그램 동작은 달라지지 않는다.

```python
def calculate_mac(pattern, filter_matrix) -> float:
```

#### 유지할 타입

바로 이해할 수 있는 타입은 유지한다.

```python
size: int
repetitions: int
epsilon: float
-> float
-> int
-> str
```

`PatternCase`, `CaseResult`, `PerformanceResult` 데이터 클래스도 유지하는 편이 좋다. 관련 값을 이름으로 묶어 전달하므로 여러 딕셔너리 키를 외우는 것보다 설명하기 쉽다.

#### Python 3.8 호환 주의

프로젝트는 Python 3.8 이상을 요구하므로 다음 내장 제네릭 표기로 무작정 바꾸면 안 된다.

```python
list[list[float]]
dict[str, object]
```

이 표기는 기본적으로 Python 3.9 이상에서 지원한다. Python 3.8 호환을 유지하려면 다음 중 하나를 선택한다.

- 복잡한 매개변수 타입 힌트를 생략한다.
- 기존 `List`, `Dict` 중 간단한 표현만 사용한다.
- `int`, `float`, `str` 같은 기본 타입만 유지한다.

현재 목표에는 복잡한 타입만 생략하는 방식이 가장 간단하다.

### 반드시 유지할 검증

다음 검증까지 제거하면 안 된다.

- 사용자 입력의 열 개수와 숫자 변환 검사
- 사용자 입력의 NaN·무한대 검사 유지 여부 검토
- JSON의 필수 키와 라벨 검사
- JSON 패턴과 필터의 정사각형·크기 일치 검사
- 성능 측정 전 패턴과 필터 크기 검사
- epsilon이 0보다 큰지 확인

특히 `validate_square_matrix()`는 JSON 크기와 스키마 검증 요구를 충족하므로 유지한다.

### 예상 수정 파일

- `src/mini_npu.py`: `_validated_number()` 제거, 판정 함수와 타입 표현 단순화
- `src/data_loader.py`: 꼭 필요하지 않은 `Mapping`, `Any`, 중첩 타입 축소
- `src/performance.py`: 긴 매개변수·반환 타입 축소
- `src/pattern_generator.py`: 실행 중 저장소 타입을 쉬운 주석과 함께 정리

## 8. 유지하는 것이 좋은 현재 구현

단순화를 진행하더라도 다음 구조는 미션에 직접 필요하거나 설명하기 쉬우므로 유지한다.

- `calculate_mac()`: 이중 반복문으로 위치별 곱셈과 누적
- `read_matrix()`: 오류가 있는 행만 재입력
- JSON 케이스 구성: 키·expected·필터·행렬 크기 검증
- JSON 케이스 반복: 오류 케이스만 FAIL 처리하고 다음 케이스 계속 진행
- 2차원·1차원 측정 함수 분리: 하나로 합치려면 함수 전달 등 더 어려운 구조가 필요함
- 필터 생성 공식: 가운데 행·열과 두 대각선을 직접 비교
- `DataLoadError`와 `DataValidationError`: 파일 전체 오류와 케이스 데이터 오류 구분
- `PatternCase`, `CaseResult`, `PerformanceResult`: 관련 값을 이름으로 묶어 전달
- 워밍업: 구현이 단순하고 첫 실행 영향을 줄이는 측정 준비 과정
- 표준편차: 10회 측정값의 변동을 보여주는 이해 가능한 통계

전체 소스를 한 파일로 합치거나 데이터 클래스를 모두 중첩 딕셔너리로 바꾸는 방식은 권장하지 않는다. 현재 복잡성의 주원인은 파일 분리가 아니라 일부 확장 기능이 공식 핵심 흐름에 연결된 점이다.

각 단계는 다음 절차로 진행한다.

```text
한 항목의 수정 범위 확정
→ 해당 코드와 관련 문서만 수정
→ 사용자가 수동 실행
→ 기존 핵심 결과와 대조
→ 실제 로그 반영
→ 다음 항목 진행
```

### 단계별 검증 기준

| 단계 | 확인할 내용 |
|---:|---|
| 1 | 메뉴 실행 순서와 관계없이 필수 네 크기가 같은 기준 입력을 사용하는가 |
| 2 | 메뉴 3 생성 → 메뉴 1 저장 필터 사용 흐름이 명확한가 |
| 3 | 평균·표준편차·N²·반복 횟수가 올바르게 출력되는가 |
| 4 | README에서 공식 결과와 추가 실험이 쉽게 구분되는가 |
| 5 | 사용자 입력·JSON 판정·epsilon 결과가 기존과 같은가 |

## 12. 최종 목표 구조

단순화가 끝나면 동료평가에서 다음 정도로 전체 프로그램을 설명할 수 있어야 한다.

```text
1. 사용자 입력이나 JSON에서 행렬을 읽고 검증합니다.
2. 이중 반복문으로 같은 위치를 곱하고 더해 Cross/X 점수를 계산합니다.
3. 두 점수 차이가 epsilon보다 작으면 UNDECIDED로 판정합니다.
4. JSON 모드는 정규화한 expected와 판정을 비교해 PASS/FAIL을 집계합니다.
5. 공식 성능은 고정된 네 크기의 순수 MAC을 각각 10회 측정합니다.
6. 보너스로 1차원 MAC과 생성한 필터의 재사용 결과를 별도로 확인합니다.
```

이 구조는 미션의 요구사항을 유지하면서 실행 순서 의존성, 숨은 자동 대체와 과도한 통계 설명을 줄이는 방향이다.
