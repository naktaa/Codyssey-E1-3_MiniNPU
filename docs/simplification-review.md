# Mini NPU 구현 단순화 결정

이 문서는 미션 요구사항과 두 보너스를 유지하면서 코드와 설명을 단순화하기 위해 확정한 기준을 기록한다. 2026-08-13 코드에 반영했으며 실제 실행 결과는 사용자 재검증 전이다.

## 결정 요약

| 항목 | 최종 결정 |
|---|---|
| JSON 로드 | 프로그램 시작 시 선행 로드하지 않고 메뉴 2 진입 시 한 번 읽어 모드 안에서 재사용 |
| 직접 입력 | 3×3 필터·패턴을 지역 변수로만 사용하고 실행 중 공용 저장소에 남기지 않음 |
| 생성 저장소 | 메뉴 3 또는 모드 1 하위 2번에서 만든 크기별 필터만 보관 |
| 모드 1 하위 2번 | JSON을 조회하지 않고 저장 생성 필터를 사용하거나 없으면 즉시 생성 |
| 성능 입력 | 이미 존재하는 크기별 Cross/X 필터 두 개를 재사용 |
| 측정 크기 | 3×3 기본 필터와 JSON 필터를 우선하고 없는 생성 크기만 추가 |
| CV | 평균 대비 표준편차의 상대 크기를 참고하기 위해 유지 |
| 반복 횟수 | 모드 1·2 모두 `PERFORMANCE_REPETITIONS` 하나를 공유하고 워밍업은 별도 유지 |
| 묶음 실험 | 코드와 증거는 유지하고 README에는 목적과 링크만 간단히 작성 |
| 입력·JSON 검증 | 미션에서 요구하거나 안전한 실행에 필요한 검증은 유지 |
| 점수 검증 | 반복 타입 변환은 제거하고 epsilon 양수와 MAC 결과 유한성만 확인 |
| 타입 힌트 | 데이터 클래스와 간단한 기본 타입은 유지하고 긴 중첩 타입은 축소 |

## 1. 데이터와 저장소

### JSON 데이터

`data.json`은 메뉴 2가 시작될 때 `load_data()`로 한 번 읽는다. 읽은 `document`를 케이스 검증과 판정에 계속 사용하며 패턴별로 파일을 다시 열지 않는다. 성능 분석은 JSON 내용을 사용하지 않는다.

프로그램 시작 시 미리 읽지 않는 이유는 다음과 같다.

- 모드 1과 메뉴 3을 JSON 파일 상태와 독립적으로 실행할 수 있다.
- JSON 파일 오류가 JSON 분석 모드에만 영향을 준다.
- 메뉴 2를 다시 선택하면 최신 파일 내용을 읽을 수 있다.
- 애플리케이션 전체가 공유하는 캐시 상태를 만들 필요가 없다.
- 파일 읽기는 공식 MAC 타이머 밖이므로 선행 로드해도 성능 이점이 없다.

### 직접 입력

모드 1 하위 1번은 필수 미션의 3×3 직접 입력 흐름이다. 입력한 Cross/X 필터와 패턴은 판정과 성능 출력 동안 지역 변수로만 유지한다. 다른 모드에서 재사용하거나 생성 저장소에 넣지 않는다.

### 생성 데이터

실행 중 저장소는 생성 기능과 관련된 데이터만 보관한다.

```text
크기 N
→ 생성 Cross/X 필터
```

같은 크기를 메뉴 3에서 다시 생성하면 필터를 교체한다. 사용자 패턴은 판정할 때만 지역 변수로 사용한다. 프로그램을 종료하면 생성 필터는 사라지며 `data.json`은 수정하지 않는다.

## 2. 사용자 입력 모드

### 하위 1번: 직접 입력

```text
3×3 필터 A 입력
→ 3×3 필터 B 입력
→ 3×3 패턴 입력
→ 점수·판정·성능 출력
```

생성 저장소와 JSON의 영향을 받지 않는다.

### 하위 2번: 생성 필터 사용

```text
N 입력
→ 해당 크기의 생성 필터가 있으면 사용
→ 없으면 Cross/X 필터 즉시 생성 및 저장
→ 사용자 패턴 입력
→ 점수·판정·성능 출력
```

기존의 `저장소 → JSON 탐색 → 오류 시 자동 생성` 흐름에서 JSON 탐색을 제거했다. JSON 손상이나 특정 크기 누락이 사용자 모드에서 숨은 자동 생성으로 대체되지 않는다.

메뉴 3은 필터 모양을 미리 확인하고 같은 크기를 명시적으로 교체하는 진입점으로 유지한다. 모드 1 하위 2번에서도 없으면 생성할 수 있으므로 메뉴 3을 반드시 먼저 실행할 필요는 없다.

## 3. 기존 필터 기반 성능 분석

성능 분석은 패턴을 사용하지 않고 같은 크기의 Cross/X 필터 두 개를 MAC 입력으로 사용한다. 별도 N×N 기준 행렬을 만들지 않고 이미 존재하는 데이터를 재사용한다.

- 3×3: 코드 내부 기본 Cross/X 필터
- 5×5·13×13·25×25: `data.json`에서 한 번 읽은 Cross/X 필터
- 그 밖의 크기: 실행 중 저장된 생성 Cross/X 필터
- 같은 크기가 JSON과 생성 저장소에 모두 있으면 JSON 필터 우선
- 2차원 MAC 성능: Cross/X 필터를 이중 반복문으로 측정
- 1차원 MAC 성능: 같은 두 필터를 펼쳐 단일 반복문으로 측정
- 출력 순서: 중복 없는 크기 오름차순
- 표 정렬: 한글의 터미널 표시 폭을 계산해 헤더와 값을 같은 열에 맞춤
- 모드 1 성능: 모드 2와 같은 표 출력 함수를 사용하고 제목만 `MAC 성능`으로 표시

필터 선택과 1차원 변환은 타이머 전에 끝난다. 따라서 기존 필터를 선택하는 과정은 순수 MAC 측정값에 포함되지 않는다.

## 4. 성능 통계

각 크기와 방식은 다음 조건을 사용한다.

- 입력과 크기를 타이머 전에 검증
- 같은 입력으로 10회 워밍업 후 측정에서 제외
- 순수 MAC 호출 10회를 각각 독립 측정
- 평균, 모집단 표준편차, CV, N²와 반복 횟수 출력

CV는 다음 값이다.

```text
CV(%) = 표준편차 ÷ 평균 × 100
```

표준편차가 평균 시간에 비해 어느 정도인지 참고하기 위해 유지한다. 매우 짧은 실행에서는 타이머와 운영체제 개입 때문에 CV가 민감할 수 있으므로 절대적인 품질 점수로 해석하지 않는다.

## 5. 검증과 타입 힌트

### 유지한 검증

- 사용자 입력 열 개수와 숫자 변환
- 사용자 입력 NaN·무한대 거부
- JSON 필수 키, 라벨과 최상위 구조
- JSON 패턴·필터의 정사각형 구조와 크기 일치
- 케이스 오류의 FAIL 처리와 다음 케이스 계속 진행
- 성능 측정 전 행렬 구조와 크기 확인
- 1차원 패턴과 필터 길이 일치
- 성능 반복 횟수 최소 10회
- epsilon 양수와 MAC 결과 유한성

### 정리한 검증

MAC 점수는 검증된 사용자·JSON·생성 입력에서 계산된다. `classify_scores()`가 점수를 다시 `Real`로 검사하고 `float`로 변환하던 중복 처리는 제거했다. 대신 계산 중 오버플로 등으로 비정상 결과가 생기는 경우를 막기 위해 최종 점수의 유한성은 확인한다.

### 타입 힌트

`PatternCase`, `CaseResult`, `PerformanceResult`, `GeneratedCase`처럼 관련 값을 묶는 데이터 클래스와 `int`, `float`, `str` 같은 간단한 타입은 유지한다. 함수 흐름을 읽는 데 도움을 주지 않는 긴 `Sequence[Sequence[...]]`, `Mapping`, 중첩 `Tuple` 표현은 축소했다.
