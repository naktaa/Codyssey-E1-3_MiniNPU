# Mini NPU 동료평가 학습 가이드

이 문서는 동료평가에서 프로그램을 미션 흐름대로 설명하고, 구현 근거와 실행 증거를 바로 확인하기 위한 발표·복습 자료다. 실제 제출 설명은 [README](../README.md)가 기준이며, 미션의 정확한 문구는 [미션 원문](mission-original.md)에서 확인한다.

> 현재 상태: 기능 구현은 완료됐지만, 검증·워밍업을 측정에서 제외하도록 바꾼 뒤의 공식 2차원·1차원 성능값은 아직 재측정 전이다. 동료평가에서 기존 성능 로그를 최신 공식값이라고 설명하지 않는다.

## 1. 미션을 한 문장으로 설명하기

숫자 행렬로 표현한 입력 패턴과 Cross/X 필터의 같은 위치 값을 곱해 모두 더한 MAC 점수를 비교하고, 사용자 입력과 JSON 데이터의 패턴을 판정하며 행렬 크기에 따른 연산 시간을 분석하는 콘솔 프로그램이다.

## 2. 평가 때 설명할 전체 흐름

```text
숫자 행렬 입력
  ├─ 사용자 입력: 행별 숫자·열 개수 검증
  └─ data.json: 키·라벨·스키마·행렬 크기 검증
          ↓
Cross 필터 MAC 점수 + X 필터 MAC 점수
          ↓
epsilon으로 두 점수 비교
          ↓
Cross / X / UNDECIDED 판정
          ↓
JSON 모드는 expected와 비교해 PASS / FAIL 집계
          ↓
검증과 I/O를 제외한 순수 MAC 성능 측정
```

설명 순서는 다음과 같이 잡으면 자연스럽다.

1. 사람에게 보이는 Cross/X 모양을 컴퓨터가 처리할 숫자 행렬로 바꾼다.
2. 입력과 필터의 같은 위치를 곱하고 모두 누적해 유사도 점수를 만든다.
3. Cross 점수와 X 점수를 epsilon 정책으로 비교해 최종 라벨을 정한다.
4. JSON 모드에서는 외부 라벨을 내부 표준 라벨로 바꾸고 expected와 비교한다.
5. 크기별 순수 MAC 시간을 측정해 N² 연산 수와 실제 시간의 관계를 해석한다.
6. 보너스로 1차원 접근 방식과 Cross/X 필터 생성·재사용을 보여준다.

## 3. 미션 원문이 요구하는 설명 항목

| 설명할 항목 | 핵심 답변 | 구현 근거 |
|---|---|---|
| MAC이란 무엇인가 | 같은 위치의 값을 곱하고 결과를 누적해서 더하는 Multiply-Accumulate 연산이다. | [`calculate_mac()`](../src/mini_npu.py) |
| AI에서 MAC이 중요한 이유 | 신경망의 가중합, 행렬 연산과 합성곱처럼 같은 형태의 곱셈·누적이 매우 많이 반복되기 때문이다. | [미션 원문](mission-original.md) |
| 점수가 유사도를 나타내는 원리 | 입력과 필터가 같은 위치에서 함께 큰 값을 가지면 곱의 합이 커진다. 두 필터 중 점수가 큰 쪽을 더 유사하다고 본다. | [사용자 모드 실행 로그](../evidence/manual-mode-success.md) |
| JSON 키 규칙 | `size_N_idx`에서 N을 꺼내 `filters.size_N`의 필터를 선택한다. | [`parse_pattern_size()`와 `get_filter_pair()`](../src/data_loader.py) |
| 라벨 정규화 이유 | `+`, `cross`, `x`처럼 표현이 다른 외부 값을 `Cross`, `X`로 통일해야 비교와 출력 규칙이 단순하고 일관된다. | [JSON 로드 로그](../evidence/json-load.md) |
| epsilon이 필요한 이유 | 실수 계산은 이진 표현과 연산 순서 때문에 수학적으로 같은 값도 아주 작게 달라질 수 있어 `==`만으로 동점을 판단하면 불안정하다. | [`classify_scores()`](../src/mini_npu.py) |
| O(N²)인 이유 | N개 행의 각 N개 열을 한 번씩 방문하므로 위치별 MAC 횟수가 N×N이다. | [`calculate_mac()`](../src/mini_npu.py) |
| 실패 원인 분류 | 데이터·스키마 오류, 계산·판정 로직 오류, 부동소수점·비교 정책 문제를 분리해서 본다. | [JSON 분석 로그](../evidence/json-analysis.md) |
| 결과 리포트 형식 | 콘솔에는 전체·통과·실패 수와 실패 목록을, README에는 실패 원인과 시간 복잡도를 10줄 이상 설명해야 한다. 실패가 0건이어도 그 이유를 설명한다. | [README 결과 리포트](../README.md) |

## 4. 데이터와 프로그램 구조

### 행렬 표현

행렬은 Python의 2차원 리스트 또는 튜플로 표현한다. `pattern[row][column]`처럼 특정 위치를 읽을 수 있고, 같은 구조로 3×3·5×5·13×13·25×25를 처리한다.

```python
cross_3x3 = [
    [0.0, 1.0, 0.0],
    [1.0, 1.0, 1.0],
    [0.0, 1.0, 0.0],
]
```

## 5. 사용자 입력 모드

### 입력과 검증

기본 직접 입력은 Cross 필터, X 필터, 패턴을 각각 3행씩 받는다. 한 행마다 다음 조건을 확인하고 잘못된 행만 다시 받는다.

- 값이 정확히 N개인가
- 모든 값을 `float`로 변환할 수 있는가
- `NaN`, 양의 무한대와 음의 무한대가 아닌 유한한 값인가

행 하나의 오류 때문에 이미 입력한 전체 행렬을 버리지 않는 것이 핵심이다. 실제 재입력 흐름은 [잘못된 입력 로그](../evidence/invalid-input.md)에서 확인한다.

### 대표 실행 결과

실제 로그의 대표 입력에서는 Cross 점수 `3.0`, X 점수 `6.0`이 계산되어 `X`로 판정됐다. 발표에서는 점수 전체 자릿수를 나열하기보다 유효한 소수 첫째 자리까지만 설명하고, 전체 콘솔 출력은 [사용자 모드 실행 로그](../evidence/manual-mode-success.md)로 연결한다.

### 설명할 포인트

- 입력 검증은 값을 안전한 행렬로 만드는 단계다.
- `calculate_mac()`은 이미 검증된 같은 크기 행렬을 받는 순수 계산 함수다.
- 판정은 계산과 분리되어 `classify_scores()`가 담당한다.
- 성능 시간은 Cross 필터와의 MAC 한 번을 대상으로 하며, 두 필터를 이용한 전체 판정 시간은 아니다.

## 6. MAC 계산과 판정

### MAC 계산식

N×N 패턴 `P`와 필터 `F`의 점수는 다음과 같다.

```text
score = Σ(i=0..N-1) Σ(j=0..N-1) P[i][j] × F[i][j]
```

코드는 이중 반복문으로 모든 위치를 방문한다.

```python
score = 0.0
for row_index in range(size):
    for column_index in range(size):
        score += pattern[row_index][column_index] * filter_matrix[row_index][column_index]
```

NumPy 같은 외부 라이브러리를 사용하지 않은 이유는 이번 미션이 MAC의 동작을 반복문으로 직접 구현하는 것을 요구하기 때문이다.

이 프로그램은 입력 행렬과 필터 한 쌍을 같은 위치에서 비교하는 MAC 원리의 학습용 시뮬레이터다. 실제 신경망 전체나 필터를 이미지의 여러 위치로 이동하는 완전한 합성곱 연산까지 구현한 것은 아니다.

### 왜 검증 함수와 계산 함수를 분리했는가

`validate_square_matrix()`는 데이터가 숫자로 된 정사각형인지 확인하고, `calculate_mac()`은 곱셈과 누적만 한다. 역할을 분리하면 일반 판정에서는 입력 단계에서 검증한 데이터를 바로 계산할 수 있고, 성능 측정에서는 검증을 타이머 전에 한 번만 수행할 수 있다.

성능 측정 함수가 MAC을 다시 구현하는 것은 아니다. 검증 → 워밍업 → `calculate_mac()` 호출 전 타이머 시작 → 호출 직후 타이머 종료 → 통계 계산을 관리하는 측정용 감싸기 함수다.

### epsilon 판정

현재 기준은 `1e-9`다.

```text
abs(Cross 점수 - X 점수) < 1e-9  → UNDECIDED
Cross 점수 > X 점수              → Cross
그 외                            → X
```

여기서 비교식은 `<`이므로 차이가 정확히 `1e-9`인 경우는 동점이 아니다. epsilon은 계산 오차를 없애는 값이 아니라, 어느 범위까지 같은 점수로 취급할지 정한 판정 정책이다.

## 7. data.json 일괄 분석

### 한 케이스의 처리 순서

1. 루트의 `data.json`을 UTF-8로 읽는다.
2. 최상위 `filters`와 `patterns`가 객체인지 확인한다.
3. `size_N_idx` 키에서 N을 추출한다.
4. `input`과 `expected`가 있는지 확인한다.
5. 입력 행렬이 N×N 정사각형인지 확인한다.
6. `filters.size_N`에서 Cross/X 필터를 찾고 크기를 확인한다.
7. 외부 라벨을 `Cross` 또는 `X`로 정규화한다.
8. 두 MAC 점수를 계산하고 epsilon으로 판정한다.
9. 판정과 expected가 같으면 PASS, 다르면 FAIL로 기록한다.
10. 모든 케이스가 끝나면 전체·통과·실패 수와 실패 목록을 출력한다.

### 라벨 정규화

```text
expected "+" 또는 "cross"  → Cross
expected "x"               → X
filter key "cross"          → Cross
filter key "x"              → X
```

정규화하지 않으면 의미가 같은 `+`와 `Cross`가 문자열 비교에서는 다른 값이 되어 정상 케이스가 FAIL이 될 수 있다. 공백 제거와 대소문자 통일도 외부 표현 차이가 내부 로직에 번지는 것을 막는다.

### 오류 처리 범위

- 파일 없음·권한·UTF-8·JSON 문법·최상위 구조 오류: 분석 모드를 안전하게 끝내고 메뉴로 돌아간다.
- 개별 패턴의 키·필수 값·행렬·필터 오류: 해당 케이스만 FAIL로 기록하고 다음 케이스를 계속 처리한다.
- 유효한 케이스의 계산 오류: 해당 케이스만 FAIL로 기록한다.

파일 전체를 읽을 수 없는 문제와 특정 케이스 하나의 문제를 구분한 이유는, 한 건의 잘못된 데이터 때문에 나머지 정상 데이터를 분석하지 못하는 일을 피하기 위해서다. 케이스 단위 오류 흐름은 코드로 구현됐지만 별도 오류 실행 로그는 사용자 결정에 따라 만들지 않았다.

## 8. 실제 JSON 결과와 FAIL 원인

현재 `data.json`은 5×5·13×13·25×25 필터와 크기별 패턴 2개씩, 총 6개 케이스를 가진다. 실제 분석 결과는 PASS 3건, FAIL 3건이다.

| 케이스 | Cross | X | 판정 | expected | 결과 |
|---|---:|---:|---|---|---|
| `size_5_1` | 0.9 | 0.9 | UNDECIDED | X | FAIL |
| `size_5_2` | 8.9 | 0.1 | Cross | Cross | PASS |
| `size_13_1` | 0.3 | 14.7 | X | X | PASS |
| `size_13_2` | 7.5 | 7.5 | UNDECIDED | Cross | FAIL |
| `size_25_1` | 4.9 | 4.9 | UNDECIDED | X | FAIL |
| `size_25_2` | 52.9 | 0.1 | Cross | Cross | PASS |

세 FAIL은 스키마 오류나 MAC 구현 오류가 아니다. Cross와 X 점수가 epsilon 범위 안에서 같아 `UNDECIDED`가 됐지만 데이터의 expected는 Cross 또는 X라는 확정 라벨이어서 불일치한 결과다. 즉, 현재 실패의 직접 원인은 데이터의 기대 라벨과 프로그램의 명시적인 동점 정책이 맞지 않는 것이다. 전체 출력은 [JSON 분석 로그](../evidence/json-analysis.md)에서 확인한다.

### 실패를 진단하는 순서

1. 데이터·스키마: 키가 `size_N_idx`인지, input/expected와 대응 필터가 있는지, 행렬 크기가 맞는지 본다.
2. 로직: 키에서 N을 잘 추출했는지, 올바른 필터를 골랐는지, 모든 위치를 한 번씩 곱했는지 확인한다.
3. 수치 비교: 두 점수 차이와 epsilon을 확인하고 `UNDECIDED` 정책이 expected와 충돌하는지 본다.

실패를 무조건 코드 버그로 보지 않고 어느 단계의 불일치인지 구분하는 것이 미션의 학습 목표다. 만약 실패가 0건이라면 정규화가 모든 외부 라벨을 올바르게 통일했고, epsilon 정책으로 나온 판정이 모든 expected와 일치했다는 근거를 설명해야 한다.

## 9. 성능 측정

### 공식 측정 파이프라인

```text
측정 입력 선택
  → 행렬 구조와 크기 검증 1회
  → 같은 입력으로 MAC 10회 워밍업(측정 제외)
  → [타이머 시작 → calculate_mac() 1회 → 타이머 종료] × 10회
  → 평균·모집단 표준편차·CV 계산
```

JSON 파싱, 스키마 검증, 1차원 변환, `print()`와 워밍업은 측정 시간에 들어가지 않는다. 타이머 안에는 `calculate_mac()`의 위치별 곱셈과 누적만 들어간다. `time.perf_counter_ns()`를 사용해 짧은 구간을 단조 증가하는 고해상도 시계로 측정하고 ns를 ms로 변환한다.

### 표의 각 열

- 평균 시간(ms): 독립 측정 10개의 산술평균
- 표준편차(ms): 10개 측정값 전체를 이번 실행의 모집단으로 본 `statistics.pstdev()` 값
- CV(%): `표준편차 ÷ 평균 × 100`, 크기가 다른 평균 사이의 상대 변동을 보는 보조 지표
- N² 연산 수: 3×3은 9, 5×5는 25, 13×13은 169, 25×25는 625
- 반복 횟수: 공식 측정은 크기별 10회

표의 N²는 방문한 위치, 즉 MAC 단위의 수를 뜻한다. 곱셈과 덧셈을 각각 별도의 기본 연산으로 세려는 표가 아니므로 `2N²`로 표시하지 않는다.

### O(N²) 해석

행렬 한 변 N이 커지면 이중 반복문이 N×N개 위치를 방문한다. 예를 들어 13×13은 169개, 25×25는 625개 위치를 처리하므로 위치 수는 약 `625 ÷ 169 ≈ 3.70배`다. 따라서 입력 크기 N에 대한 이론적 시간 복잡도는 O(N²)다.

실제 시간 비율이 N² 비율과 정확히 같을 필요는 없다. 매우 짧은 Python 함수 호출과 타이머 자체의 고정 비용, 운영체제 스케줄링, 백그라운드 작업과 CPU 상태가 측정에 섞일 수 있기 때문이다. O(N²)는 입력이 커질 때 연산량이 증가하는 경향을 설명하며, 한 번의 측정값이 정확히 같은 배율을 보여야 한다는 뜻이 아니다.

### 워밍업과 한계

워밍업은 첫 실행 때 생길 수 있는 인터프리터·캐시 상태 영향을 줄이기 위한 준비 실행이다. 하지만 운영체제 개입과 CPU 상태 변화까지 없애지는 못한다. 특히 3×3처럼 매우 짧은 계산은 타이머 시작·종료 비용의 상대적 비중이 크므로 평균과 표준편차를 함께 보고 과도하게 일반화하지 않는다.

### 아직 채워야 할 공식 결과

최신 공식 결과는 새 Python 프로세스에서 메뉴 2를 먼저 실행해 다시 수집해야 한다. 기존 [10회 성능 로그](../evidence/ten-run-performance.md)는 계산 함수 안에 검증이 포함됐던 이전 조건의 기록이므로 최신 공식값으로 사용하지 않는다.

| 방식 | 3×3 평균±표준편차 | 5×5 평균±표준편차 | 13×13 평균±표준편차 | 25×25 평균±표준편차 |
|---|---|---|---|---|
| 2차원 MAC | 재측정 필요 | 재측정 필요 | 재측정 필요 | 재측정 필요 |
| 1차원 MAC | 재측정 필요 | 재측정 필요 | 재측정 필요 | 재측정 필요 |

## 10. 보너스 1: 1차원 MAC

2차원 행렬을 행 순서대로 길이 N²의 리스트로 한 번 펼친 뒤 단일 반복문으로 같은 인덱스를 곱한다.

```text
2차원: pattern[row][column] × filter[row][column]
1차원: pattern[index] × filter[index]
```

두 방식 모두 모든 N²개 값을 처리하므로 시간 복잡도는 O(N²)로 같다. 기대하는 차이는 복잡도 등급의 변화가 아니라, 중첩 인덱싱을 단일 인덱싱으로 단순화했을 때의 실제 실행 시간 차이다.

공정한 비교를 위해 같은 입력과 같은 반복 횟수를 사용하고, 1차원 변환은 측정 전에 한 번만 수행한다. 변환까지 매번 시간에 넣으면 MAC 접근 방식이 아니라 데이터 준비 비용까지 비교하게 된다. 최신 2차원·1차원 공식 비교는 재측정 후 작성한다.

## 11. 보너스 2: 필터 생성기

기능 이름은 미션과 현재 설계에 맞춰 `필터 생성기`로 유지한다. 3 이상의 홀수 N을 받아 다음 조건으로 0과 1의 필터를 만든다.

- Cross: `row == N // 2` 또는 `column == N // 2`
- X: `row == column` 또는 `row + column == N - 1`

홀수만 받는 이유는 가운데 행과 가운데 열이 하나로 명확하기 때문이다. 생성 결과는 `matrix_store`에 저장되어 같은 실행의 사용자 모드와 성능 분석에서 재사용된다. `data.json`을 수정하지 않으며 프로그램을 종료하면 사라진다. 실제 흐름은 [생성 필터 성능 재사용 로그](../evidence/generated-filter-performance.md)와 [사용자 모드 재사용 로그](../evidence/manual-nxn-filter-flow.md)에서 확인한다.

## 12. 비공식 묶음 벤치마크

`benchmark_batch.py`는 미션의 공식 결과가 아니라 측정 방식의 영향을 살펴보기 위한 추가 실험이다.

- 공식 방식: MAC 한 번마다 타이머를 시작하고 끝내 개별 호출 시간 10개를 얻는다.
- 묶음 방식: 타이머 한 쌍 안에서 MAC을 10·100·1,000번 실행하고 전체 시간을 호출 수로 나눈다. 이 묶음을 10번 측정한다.

묶음 방식은 타이머 비용을 여러 호출에 나눌 수 있지만, 묶음 안의 Python 반복문 비용이 포함되고 개별 호출의 순간적인 지연은 평균에 가려질 수 있다. 공식 표준편차는 개별 호출 시간의 변동이고 묶음 표준편차는 묶음별 호출당 평균의 변동이므로 두 CV를 같은 통계처럼 직접 비교하지 않는다.

실제 보조 결과와 한계는 [묶음 전용 로그](../evidence/batch-benchmark.md)와 [분리 전 비교 로그](../evidence/individual-batch-comparison.md)에 있다.

## 13. 1000×1000 행렬과 CPU/NPU

### 대규모 행렬

1000×1000은 필터 하나당 1,000,000개 위치를 처리한다. Cross와 X 점수를 모두 계산하면 약 2,000,000개 위치 연산이 필요하다.

- 복사 최소화: 반복 계산할 입력과 필터를 다시 만들지 않고 재사용한다.
- 접근 구조 단순화: 필요하다면 1차원 변환을 측정 전에 한 번만 수행한다. 복잡도는 여전히 O(N²)다.
- 더 큰 작업 대응: 입력과 반복 수가 훨씬 커지면 병렬 처리나 전용 가속기를 고려한다.

### CPU와 NPU

CPU는 여러 종류의 작업을 수행하는 범용 프로세서이며 멀티코어와 벡터 명령으로 병렬 처리도 할 수 있다. 다만 이 프로그램의 Python 이중 반복문은 그 병렬 능력을 직접 활용하지 않는다.

NPU는 같은 형태의 MAC을 대량 병렬 처리하도록 특화된 장치다. 큰 행렬과 반복 작업에서 장점이 있을 수 있지만 이 미션은 실제 NPU에서 측정하지 않았으므로, 구체적인 속도 차이나 전환점을 검증한 사실처럼 말하지 않는다.

## 14. 예상 질문과 답변

### 왜 `calculate_mac()` 안에서 행렬을 검증하지 않나요?

성능 측정에서 반복마다 검증 시간이 섞이지 않게 하기 위해서다. 사용자 입력은 입력 단계에서, JSON은 케이스 구성 단계에서, 성능 분석은 타이머 시작 전에 검증한다. `calculate_mac()`은 검증된 입력의 순수 곱셈·누적만 담당한다.

### 그렇다면 검증이 빠진 위험은 없나요?

공개 실행 경로에서는 모두 계산 전에 검증한다. 대신 `calculate_mac()`을 단독으로 직접 호출하는 코드는 같은 크기의 검증된 행렬을 전달해야 한다는 전제가 있다. 역할 분리에서 생기는 명시적인 계약이다.

### 왜 계산 함수와 측정 함수가 따로 필요한가요?

계산 함수는 실제 기능과 여러 모드가 공통으로 재사용한다. 측정 함수는 검증, 워밍업, 타이머와 통계를 관리하면서 그 계산 함수를 호출한다. 하나로 합치면 일반 판정에도 타이머 로직이 섞이거나, 측정마다 검증이 반복될 수 있다.

### 왜 Cross와 X 두 번의 계산이 아니라 Cross MAC 한 번만 측정하나요?

미션 표가 요구하는 대상은 크기별 MAC 연산 함수 호출 구간이다. 두 필터 판정 전체가 아니라 동일한 단위의 MAC 한 번을 측정해야 크기별 N² 작업량을 비교하기 쉽다. 출력에도 측정 대상을 명시한다.

### 왜 `==`로 동점을 비교하지 않나요?

십진 실수 일부는 이진 부동소수점으로 정확히 표현되지 않는다. 계산 결과가 수학적으로 같아도 극소 차이가 생길 수 있으므로 epsilon보다 작은 차이는 같은 점수로 취급한다.

### 현재 FAIL 3건은 프로그램 오류인가요?

아니다. 세 케이스 모두 유효한 데이터이며 실제 두 점수가 동점이다. 프로그램은 명시된 epsilon 정책대로 `UNDECIDED`를 반환했고, 확정 라벨인 expected와 달라 FAIL이 됐다.

### 1차원으로 바꾸면 O(N)이 되나요?

아니다. 리스트 길이가 N²이므로 단일 반복문도 N²번 돈다. 표기만 이중 반복문에서 단일 반복문으로 바뀌었을 뿐 입력 한 변 N에 대한 복잡도는 O(N²)다.

### 반복 횟수가 많을수록 항상 더 안정적인가요?

항상 그렇지는 않다. 평균화 효과는 커질 수 있지만 측정 시간이 길어지면서 스케줄링과 CPU 상태 변화가 추가로 개입할 수 있다. 실제 묶음 실험에서도 1,000회가 모든 크기에서 가장 낮은 CV를 보이지 않았다.

### 왜 표준편차와 CV를 모두 보여주나요?

표준편차는 ms 단위의 절대 변동을, CV는 평균 대비 상대 변동을 보여준다. 단, 평균이 매우 작은 측정에서는 작은 절대 변화도 CV를 크게 만들 수 있어 원시 평균과 함께 해석해야 한다.
