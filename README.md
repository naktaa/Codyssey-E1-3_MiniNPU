# Mini NPU Simulator

E1-3 미션용 Python 콘솔 애플리케이션입니다. 2차원 패턴과 Cross/X 필터의 MAC 점수를 반복문으로 계산하고, 사용자 입력과 `data.json` 일괄 분석을 지원합니다.

> 현재 상태: 필수 기능과 두 보너스 구현 완료. 10회 독립 측정의 평균·표준편차와 한글 성능 표를 사용자 실행으로 확인했습니다.

## 실행 환경

| 항목 | 상태 |
|---|---|
| Python 요구 버전 | 3.8 이상 |
| 기존 실행 확인 버전 | 3.12.13 |
| 운영체제 | macOS Sequoia 15.7.4 |
| CPU | 3.1GHz 6코어 Intel Core i5 |
| 메모리 | 32GB 2667MHz DDR4 |
| 외부 라이브러리 | 사용하지 않음 |

환경 정보는 사용자가 제공한 [macOS 환경 캡처](evidence/mac-status.png)를 기준으로 기록했으며, 장치 일련번호는 가렸습니다.

## 실행 방법

저장소 루트에서 실행합니다.

```zsh
python3 main.py
```

메뉴는 다음 네 항목으로 구성됩니다.

1. 사용자 입력 모드
2. `data.json` 일괄 분석
3. N×N Cross/X 필터 생성
4. 종료

## 핵심 구현

- `calculate_mac()`은 N×N의 같은 위치 값을 이중 반복문으로 곱하고 누적합니다.
- MAC 점수가 높을수록 입력 패턴과 해당 필터의 큰 값이 같은 위치에 많이 겹치므로, 이 시뮬레이터에서는 유사성이 높다고 판단합니다.
- 두 점수 차이가 epsilon `1e-9` 미만이면 `UNDECIDED`, 아니면 더 높은 점수의 `Cross` 또는 `X`로 판정합니다.
- 사용자 입력은 잘못된 열 개수, 숫자 형식, NaN과 무한대를 행 단위로 다시 입력받습니다.
- JSON의 expected `+`·`cross`·`x`와 필터 키 `cross`·`x`를 내부 `Cross`·`X`로 정규화합니다.
- JSON 케이스의 키·행렬·라벨 오류는 해당 케이스만 FAIL 처리하고 다음 케이스를 계속 분석합니다.
- 파일 없음, 권한, UTF-8과 JSON 문법 오류는 `분석 실패:`로 안내하고 JSON 모드만 종료합니다.
- 실행 중 생성하거나 입력한 필터와 패턴은 같은 프로그램 실행의 사용자 모드와 성능 분석에서 재사용됩니다.

### 성능 측정 기준

- 3×3·5×5·13×13·25×25와 실행 중 추가된 크기를 측정합니다.
- 각 크기와 방식에서 MAC 함수 호출 10개를 `time.perf_counter_ns()`로 각각 측정합니다.
- 10개 측정값의 산술 평균과 모집단 표준편차를 ms 단위로 계산합니다.
- 표에는 크기, 평균 시간, 표준편차, N² 연산 수와 반복 횟수를 출력합니다.
- 파일 읽기, 사용자 입력과 콘솔 출력은 측정하지 않습니다.
- 1차원 변환은 측정 전에 수행하므로 1차원 MAC 시간에 포함하지 않습니다.

## 결과 리포트

현재 판정 결과와 성능값은 사용자가 2026-08-11에 `py`로 메뉴 2를 실행한 결과입니다. 각 성능값은 MAC 함수 호출을 10회 독립 측정한 평균과 모집단 표준편차입니다.

### 핵심 결과

1. 실제 `data.json`의 전체 테스트는 6건입니다.
2. 통과는 3건, 실패는 3건이며 합계가 전체 6건과 일치합니다.
3. 실패 케이스는 `size_5_1`, `size_13_2`, `size_25_1`입니다.
4. 세 실패는 모두 Cross와 X 점수가 epsilon 범위에서 같아 `UNDECIDED`가 된 경우입니다.
5. expected는 확정 라벨 Cross 또는 X이므로 `UNDECIDED`와 일치하지 않아 FAIL로 집계됩니다.
6. 확인된 JSON 구조, 라벨 정규화와 MAC 계산 오류는 없습니다.
7. 3×3 사용자 입력에서는 Cross `3.000000`, X `6.000000`, 최종 `X` 판정을 확인했습니다.
8. 필수 네 크기의 N² 연산 수는 9·25·169·625입니다.
9. 이번 측정에서 N이 커질수록 평균 실행 시간도 증가했습니다.
10. MAC은 N×N의 모든 위치를 처리하므로 시간 복잡도는 O(N²)입니다.

### 판정 결과

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---:|---:|---|---|---|
| `size_5_1` | 0.900000 | 0.900000 | UNDECIDED | X | FAIL |
| `size_5_2` | 8.900000 | 0.100000 | Cross | Cross | PASS |
| `size_13_1` | 0.300000 | 14.700000 | X | X | PASS |
| `size_13_2` | 7.500000 | 7.500000 | UNDECIDED | Cross | FAIL |
| `size_25_1` | 4.900000 | 4.900000 | UNDECIDED | X | FAIL |
| `size_25_2` | 52.900000 | 0.100000 | Cross | Cross | PASS |

부동소수점 누적 결과는 수학적으로 같아도 아주 작은 차이가 생길 수 있어 `==` 대신 epsilon을 사용합니다. 모드 1과 모드 2는 같은 동점 기준을 사용하지만, 모드 1은 판정 불가를 출력하고 모드 2는 `UNDECIDED`를 expected와 비교해 PASS/FAIL을 결정합니다.

최신 판정과 성능 결과는 [10회 MAC 실행 로그](evidence/ten-run-performance.md), 입력 재시도는 [잘못된 입력](evidence/invalid-input.md)에 기록했습니다.

### 시간 복잡도와 측정값

| 크기 | 평균 시간(ms) | 표준편차(ms) | N² 연산 수 | 반복 횟수 |
|---|---:|---:|---:|---:|
| 3×3 | 0.019748 | 0.000796 | 9 | 10 |
| 5×5 | 0.040439 | 0.000604 | 25 | 10 |
| 13×13 | 0.225531 | 0.000231 | 169 | 10 |
| 25×25 | 0.792834 | 0.012556 | 625 | 10 |

13×13에서 25×25로 커질 때 N²는 약 3.70배, 평균 시간은 약 3.51배 증가했습니다. 실제 시간 비율이 N² 비율과 정확히 같지 않은 이유는 함수 호출, Python 반복문, 행렬 검증, 타이머 호출과 운영체제 스케줄링 같은 고정 비용 때문입니다. 특히 작은 N에서는 이 고정 비용의 비중이 상대적으로 큽니다.

### 대규모 행렬과 CPU/NPU

#### 대규모 행렬에서 생기는 문제

1000×1000 행렬은 MAC 한 번에 1,000,000개 위치를 처리합니다. 현재 판정은 패턴을 Cross와 X 필터에 각각 적용하므로 두 점수 계산에는 약 2,000,000개 위치 연산이 필요합니다. 행렬 크기가 커지면 연산 시간뿐 아니라 패턴과 두 필터를 보관하는 메모리도 함께 증가합니다.

현재 Python 리스트는 숫자 자체 외에 각 행과 원소를 가리키는 참조도 보관합니다. 따라서 같은 원소 수라도 연속된 숫자 버퍼보다 메모리 사용량과 접근 비용이 커질 수 있습니다. 또한 반복 측정마다 행렬을 다시 검증하므로 순수 곱셈·누적 외의 검증 비용도 측정 시간에 포함됩니다.

#### 고려할 수 있는 최적화 방법

- **복사와 변환 최소화:** 같은 입력을 반복 계산할 때 행렬을 매번 새로 만들지 않고 재사용합니다. 2차원에서 1차원으로 변환해야 한다면 현재 보너스처럼 측정 전에 한 번만 변환합니다.
- **접근 구조 단순화:** 1차원 리스트는 행·열의 이중 인덱싱을 하나의 인덱스로 줄입니다. 모든 N²개 원소를 처리하므로 시간 복잡도는 O(N²)로 같지만, Python에서의 인덱싱 비용을 줄일 가능성이 있습니다.
- **검증과 핵심 연산 분리:** 같은 행렬을 여러 번 계산한다면 최초 한 번만 구조를 검증하고 이후에는 MAC 반복문만 호출하는 방식을 고려할 수 있습니다. 다만 입력이 중간에 바뀌지 않는다는 조건이 필요합니다.
- **희소 필터 활용:** Cross와 X처럼 0이 많은 필터는 0이 아닌 위치만 저장하고 순회하면 실제 곱셈 수를 줄일 수 있습니다. 이는 현재 미션의 일반적인 N² 직접 반복과 다른 추가 최적화입니다.
- **블록 단위 처리:** 큰 행렬을 작은 구역으로 나누면 한 번에 다루는 작업 집합을 줄이고 캐시 지역성을 높일 수 있습니다. 전체 위치 수는 그대로지만 메모리 접근 효율을 개선할 수 있습니다.
- **병렬 처리:** 행 구간을 여러 작업으로 나눌 수 있습니다. Python 반복문은 스레드만으로 큰 효과를 얻기 어려울 수 있어 프로세스나 네이티브 연산을 검토할 수 있지만, 데이터 복사와 작업 분배 비용이 추가됩니다.

이번 미션에서는 반복문 기반 MAC의 원리와 O(N²) 특성을 확인하는 것이 목적이므로 위 방법을 코드에 추가하지 않습니다. 현재 1차원 비교만 접근 구조 단순화 실험으로 구현되어 있습니다.

#### CPU와 NPU의 처리 방식

신경망에서는 입력값과 가중치를 곱해 누적하는 MAC이 한 계층에서도 대량으로 반복됩니다. 따라서 MAC 처리량과 데이터를 연산 장치에 공급하는 메모리 대역폭이 AI 연산 성능의 중요한 요소가 됩니다.

CPU는 운영체제와 다양한 프로그램을 처리하는 범용 프로세서입니다. CPU도 여러 코어, SIMD 벡터 명령과 스레드를 사용해 병렬 계산할 수 있으므로 단순히 직렬 장치라고 볼 수 없습니다. 다만 현재 프로그램은 Python 이중 반복문으로 한 위치씩 처리하므로 CPU의 벡터 연산 능력을 직접 활용하지 못하고, 인터프리터 실행과 리스트 접근 비용의 영향을 받습니다.

NPU는 많은 곱셈·누적기를 동시에 동작시키고 중간 데이터를 가까운 내부 메모리에서 재사용하도록 설계된 AI 연산 특화 장치입니다. 같은 형태의 MAC을 대량으로 반복할 때 높은 병렬 처리량을 얻을 수 있지만, 데이터를 NPU로 전송하는 시간, 메모리 대역폭과 작은 작업에서 연산 장치가 충분히 채워지지 않는 문제가 병목이 될 수 있습니다.

작은 행렬에서는 장치 호출과 데이터 전송 준비 비용 때문에 CPU가 더 효율적일 수 있습니다. 반대로 큰 행렬이나 같은 연산을 반복하는 배치에서는 준비 비용의 비중이 줄어 NPU의 병렬 처리 장점이 커질 수 있습니다. 실제 전환점은 하드웨어와 입력 형태에 따라 달라 별도 측정이 필요합니다.

### 1차원 비교 결과

| 크기 | 2차원 평균(ms) | 2차원 표준편차(ms) | 1차원 평균(ms) | 1차원 표준편차(ms) | 속도비(2D/1D) |
|---|---:|---:|---:|---:|---:|
| 3×3 | 0.019748 | 0.000796 | 0.013336 | 0.002152 | 약 1.48배 |
| 5×5 | 0.040439 | 0.000604 | 0.030974 | 0.000269 | 약 1.31배 |
| 13×13 | 0.225531 | 0.000231 | 0.197598 | 0.000886 | 약 1.14배 |
| 25×25 | 0.792834 | 0.012556 | 0.742221 | 0.014094 | 약 1.07배 |

이번 실행에서는 네 크기 모두 1차원 평균이 더 짧았습니다. 다만 1차원 방식도 모든 N²개 원소를 처리하므로 시간 복잡도 자체는 O(N²)로 같습니다.

### N×N 필터 생성기

메뉴 3은 3 이상의 홀수 N으로 Cross와 X 필터를 생성합니다. 생성 결과는 JSON에 저장하지 않고 실행 중 메모리에만 유지하며, 사용자 모드와 성능 분석에서 재사용합니다. 3×3·5×5·7×7 생성, 5×5 교체와 생성 3×3 재사용을 사용자 실행으로 확인했습니다.
