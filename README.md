# Mini NPU Simulator

E1-3 미션용 Python 콘솔 애플리케이션입니다. 2차원 패턴과 Cross/X 필터의 MAC 점수를 반복문으로 계산하고, 사용자 입력과 `data.json` 일괄 분석을 지원합니다.

> 현재 상태: 필수 기능과 두 보너스 구현 완료. 공식 성능은 워밍업 후 단일 MAC 10회 독립 측정으로 고정했으며 새 성능값은 재측정이 필요합니다.

## 실행 환경

| 항목 | 환경 |
|---|---|
| Python 요구 버전 | 3.8 이상 |
| 실제 확인 버전 | 3.12.13 |
| 운영체제 | macOS Sequoia 15.7.4 |
| CPU | 3.1GHz 6코어 Intel Core i5 |
| 메모리 | 32GB 2667MHz DDR4 |
| 외부 라이브러리 | 사용하지 않음 |

## 실행 방법

`data.json`은 `main.py`와 같은 저장소 루트에 두고, 저장소 루트에서 다음 명령을 실행합니다.

```zsh
python3 main.py
```

메뉴는 다음 네 항목으로 구성됩니다.

1. 사용자 입력 모드
2. `data.json` 일괄 분석
3. N×N Cross/X 필터 생성
4. 종료

## 구현 요약

- 사용자 입력과 JSON 로드 단계에서 행렬 구조, 숫자와 크기를 먼저 검증합니다.
- `calculate_mac()`은 검증된 N×N 패턴과 필터의 같은 위치 값을 이중 반복문으로 곱하고 누적하는 계산만 수행합니다.
- 두 점수 차이가 epsilon `1e-9` 미만이면 `UNDECIDED`, 아니면 점수가 더 높은 `Cross` 또는 `X`로 판정합니다.
- JSON의 expected `+`·`cross`·`x`와 필터 키 `cross`·`x`를 내부 라벨 `Cross`·`X`로 정규화합니다.
- 사용자 입력의 잘못된 열 개수와 숫자 형식은 해당 행만 다시 입력받습니다. 실제 흐름은 [잘못된 행 입력 로그](evidence/invalid-input.md)에서 확인할 수 있습니다.
- NaN과 무한대도 입력 단계에서 거부하도록 구현했지만 이 확장 입력은 별도로 실행하지 않았습니다.
- JSON 케이스의 키·행렬·라벨 오류는 해당 케이스만 FAIL 처리하고 다음 케이스를 계속 분석합니다.
- 파일 없음, 권한, UTF-8과 JSON 문법 오류는 `분석 실패:`로 안내하고 JSON 모드만 종료합니다.

## 결과 리포트

### 사용자 입력 모드 결과

3×3 필터 두 개와 패턴을 직접 입력해 다음 결과를 확인했습니다. README에서는 점수를 소수 첫째 자리로 정리했으며 입력 행렬과 콘솔 원문은 [사용자 입력 모드 실행 로그](evidence/manual-mode-success.md)에 보관했습니다.

```text
[판정 결과]
Cross 점수: 3.0
X 점수: 6.0
판정: X
```

### JSON 분석 모드 결과

`data.json`의 필터 크기는 5×5·13×13·25×25이며 패턴은 총 6건입니다. 전체 집계는 다음과 같고, 케이스별 콘솔 출력과 성능 측정 원문은 [10회 MAC 실행 로그](evidence/ten-run-performance.md)에서 확인할 수 있습니다.

```text
[전체 결과]
전체 케이스: 6
통과: 3
실패: 3
판정 epsilon: 1e-09
```

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---:|---:|---|---|---|
| `size_5_1` | 0.9 | 0.9 | UNDECIDED | X | FAIL |
| `size_5_2` | 8.9 | 0.1 | Cross | Cross | PASS |
| `size_13_1` | 0.3 | 14.7 | X | X | PASS |
| `size_13_2` | 7.5 | 7.5 | UNDECIDED | Cross | FAIL |
| `size_25_1` | 4.9 | 4.9 | UNDECIDED | X | FAIL |
| `size_25_2` | 52.9 | 0.1 | Cross | Cross | PASS |

### FAIL 케이스 원인 분석

전체 6건 중 통과는 3건, 실패는 3건이며 합계가 전체 케이스 수와 일치합니다. 실패 케이스는 `size_5_1`, `size_13_2`, `size_25_1`입니다. 세 케이스 모두 Cross와 X 점수가 epsilon 범위에서 같아 `UNDECIDED`로 판정됐습니다. expected는 확정 라벨인 Cross 또는 X이므로 `UNDECIDED`와 일치하지 않아 FAIL로 집계됩니다.

부동소수점 누적 결과는 수학적으로 같아도 아주 작은 차이가 생길 수 있어 `==` 대신 epsilon을 사용합니다. 모드 1은 동점을 `판정 불가 (UNDECIDED)`로 출력하고, 모드 2는 `UNDECIDED`를 expected와 비교해 PASS/FAIL을 결정합니다. 이번 실패는 JSON 구조, 라벨 정규화 또는 MAC 계산 오류가 아니라 명시된 동점 정책에 따른 결과입니다.

### 성능 측정 결과

- 3×3·5×5·13×13·25×25와 실행 중 추가된 크기를 측정합니다.
- 각 크기의 패턴과 Cross 필터를 타이머 시작 전에 한 번 검증합니다.
- 각 크기와 방식마다 같은 입력으로 MAC을 10회 워밍업하며 워밍업 시간은 결과에서 제외합니다.
- 타이머 안에서는 검증된 입력의 `calculate_mac()` 곱셈·누적만 10회 독립 측정합니다.
- `time.perf_counter_ns()`로 구한 10개 측정값의 산술평균, 모집단 표준편차와 변동계수 CV를 계산합니다.
- 파일 읽기, 사용자 입력, 행렬 검증과 콘솔 출력은 측정 구간에서 제외합니다.

현재 코드는 순수 MAC 구간만 측정하고, 측정 전에 10회 워밍업하도록 변경됐습니다. 기존 [10회 MAC 실행 로그](evidence/ten-run-performance.md)의 성능값은 행렬 검증과 워밍업 조건이 현재 방식과 다르므로 새 측정값으로 교체하기 전까지 참고 기록으로만 보존합니다.

공식 결과를 재현할 때는 저장소 루트에서 새 Python 프로세스로 `python3 main.py`를 실행한 직후 메뉴 2를 먼저 선택합니다. 필터 생성이나 사용자 입력 모드를 먼저 사용하면 실행 중 저장된 행렬이 성능 입력에 반영될 수 있습니다. 같은 Mac과 Python 버전을 사용하고, 가능하면 전원 상태를 유지하며 무거운 백그라운드 작업을 피합니다. 워밍업은 CPython의 초기 실행·캐시 상태 차이를 줄이지만 운영체제 스케줄링, 인터럽트, CPU 클럭 변화와 다른 프로세스의 개입까지 제거하지는 않습니다.

### 성능표 해석

MAC은 N×N의 모든 위치를 한 번씩 처리하므로 연산 횟수와 시간 복잡도는 N², 즉 O(N²)입니다. 이전 검증 포함 측정에서도 행렬 크기가 커질수록 평균 시간이 증가했지만, 순수 MAC 측정값의 증가 흐름과 비율은 재실행 후 다시 분석해야 합니다.

새 측정에서도 N² 비율과 실행 시간 비율은 Python 함수·반복문 오버헤드, 타이머 호출과 운영체제 스케줄링 때문에 정확히 일치하지 않을 수 있습니다. 특히 작은 행렬에서는 이런 고정 비용의 비중이 상대적으로 큽니다. 새 표는 같은 환경에서 크기에 따른 증가 경향을 비교하는 자료로 해석합니다.

## 보너스

### 1차원 MAC 비교

2차원 패턴과 필터를 측정 전에 검증하고 행 순서의 1차원 리스트로 변환합니다. 변환된 두 리스트의 길이도 타이머 시작 전에 확인하고, 타이머 안에서는 같은 위치 값을 단일 반복문으로 곱해 누적합니다. 변환과 검증 시간은 측정에 포함하지 않으며 2차원 방식과 같은 입력, 같은 10회 반복 조건을 사용합니다.

1차원 방식도 N²개 원소를 모두 처리하므로 시간 복잡도는 O(N²)로 같습니다. 기존 비교값은 검증 포함 방식의 [10회 MAC 실행 로그](evidence/ten-run-performance.md)에 과거 기록으로 남기며, 순수 2차원·1차원 MAC의 새 비교표와 속도비는 재측정 후 반영합니다.

### 비공식 묶음 벤치마크

공식 결과와 별도로 `benchmark_batch.py`에서 같은 입력과 MAC 함수를 사용해 묶음 측정을 확인할 수 있습니다. 공식 `main.py`의 개별 호출 측정을 먼저 실행하지 않으므로 두 측정 방식이 한 프로세스에서 연속 실행될 때 생길 수 있는 순서 영향을 줄였습니다.

반복 횟수 `10`, `100`, `1000` 중 하나를 인자로 전달해 설정별 로그를 따로 수집합니다.

```zsh
python3 benchmark_batch.py 10
python3 benchmark_batch.py 100
python3 benchmark_batch.py 1000
```

- 묶음 측정: 타이머 한 쌍 안에서 인자로 받은 횟수만큼 MAC을 실행하고, 같은 묶음을 10번 측정합니다.
- 모든 설정은 측정 전에 10회 워밍업하고 검증·1차원 변환·출력을 타이머에서 제외합니다.
- 공식 일괄 분석과 묶음 프로그램은 크기·평균·표준편차·CV·N²·반복 횟수의 같은 표 형식을 사용합니다.
- 공식 표의 표준편차는 개별 MAC 호출 시간의 변동이고, 묶음 표준편차는 묶음별 호출당 평균의 변동입니다. 의미가 다르므로 두 값을 직접 같은 통계로 비교하지 않습니다.
- 묶음 측정에는 타이머 비용이 호출 수에 분산되는 대신, 타이머 안쪽에서 묶음을 실행하는 Python 반복문 비용이 포함됩니다.

표의 `반복 횟수`는 타이머 한 쌍 안의 MAC 호출 수를 뜻합니다. 묶음 표준편차를 위한 묶음 표본 수는 고정 10개이며 측정 방식 안내에 별도로 출력됩니다. 숫자는 위치 인자로 사용하며 `--10`처럼 옵션으로 쓰지 않습니다. `10`은 기능을 켜는 옵션이 아니라 MAC 호출 수라는 하나의 필수 값이기 때문입니다.

이 비교는 매우 짧은 MAC에서 타이머 오버헤드와 시스템 개입이 결과에 미치는 영향을 고찰하기 위한 실험이며 미션의 공식 성능표에는 사용하지 않습니다. 묶음 전용 10·100·1,000회 실제 결과는 [묶음 벤치마크 로그](evidence/batch-benchmark.md), 분리 전 결합형 결과는 [개별·묶음 측정 비교 로그](evidence/individual-batch-comparison.md)에 보존합니다.

기존 결합형 로그에서는 묶음 방식의 호출당 평균과 CV가 각각 24개 비교 중 20개에서 개별 호출 방식보다 낮았습니다. 특히 짧은 3×3·5×5에서는 MAC마다 사용하던 타이머 비용을 여러 호출에 분산한 영향이 크게 나타났습니다. 다만 두 CV는 측정 대상이 다르고, 일부 묶음 결과에서도 큰 변동이 발생했으므로 실제 MAC 실행이 더 안정화됐다는 의미는 아닙니다.

기존 방식의 한계와 보완 방향은 다음과 같습니다.

- 개별 호출 방식은 호출별 지연을 관찰할 수 있지만 짧은 MAC에서는 타이머 비용과 시스템 개입의 상대적 비중이 큽니다.
- 묶음 방식은 호출당 평균 처리 시간을 보기 좋지만 개별 이상 지연을 평균 안에 희석하고 Python 묶음 반복문 비용을 포함합니다.
- 기존 결합형 실행은 개별 측정 뒤 묶음 측정을 수행해 캐시, CPython 적응형 실행과 CPU 상태의 순서 영향이 섞일 수 있습니다.
- 묶음 전용 파일을 별도 프로세스로 실행해 순서 영향을 줄이고, 공식 개별 10회와 묶음 결과를 서로 다른 의미의 보조 지표로 해석합니다.

설정별 전체 수치, 예외 항목과 해석 제한은 [개별·묶음 측정 비교 로그](evidence/individual-batch-comparison.md)에서 확인할 수 있습니다.

묶음 전용 실행에서는 세 설정의 호출당 평균 범위가 모두 약 8% 이내였고, 13×13·25×25는 대부분 약 4% 이내로 비슷한 평균 경향을 보였습니다. 평균 CV는 10회 약 `1.12%`, 100회 약 `1.02%`, 1,000회 약 `1.89%`였습니다. 이번 실행에서는 100회가 가장 균형 잡혔지만 25×25 2차원에 `4.09%`의 예외가 있었고, 1,000회도 1차원 5×5·13×13에서 CV가 커졌습니다. 따라서 반복 수를 늘린다고 항상 더 안정되는 것은 아닙니다.

분리 전 10회 묶음 2차원 13×13 CV `20.21%`는 묶음 전용 실행에서 `0.79%`로 낮아졌습니다. 이는 개별 측정을 먼저 실행하지 않는 분리 방향과 일치하지만, 실행 시점의 시스템 상태도 달랐으므로 분리만의 효과로 단정하지 않습니다. 상세 수치와 원인 분석은 [묶음 벤치마크 로그](evidence/batch-benchmark.md)에서 확인할 수 있습니다.

### 필터 생성기

메뉴 3은 3 이상의 홀수 N을 입력받아 Cross와 X 필터를 생성합니다. 생성 결과는 `data.json`에 쓰지 않고 실행 중 메모리에만 보관하며, 같은 프로그램 실행의 사용자 입력 모드와 성능 분석에서 재사용합니다.

3×3·7×7 생성과 성능 분석 재사용은 [생성 필터와 성능 재사용 로그](evidence/generated-filter-performance.md), 자동 생성 필터의 사용자 모드 재사용은 [N×N 자동 생성·저장 필터 로그](evidence/manual-nxn-filter-flow.md)에서 확인할 수 있습니다.

## 대규모 행렬 검토

1000×1000 행렬은 필터 하나와의 MAC에 1,000,000개 위치를 처리합니다. 현재 판정은 Cross와 X 필터를 각각 적용하므로 두 점수 계산에는 약 2,000,000개 위치 연산이 필요합니다. 행렬 크기가 커질수록 실행 시간과 행렬 저장 공간도 함께 증가합니다.

- **복사와 변환 최소화:** 같은 입력을 반복 계산할 때 행렬을 다시 만들지 않고 재사용합니다. 1차원 변환이 필요하다면 측정 전에 한 번만 수행합니다.
- **접근 구조 단순화:** 2차원 행렬을 1차원으로 변환하면 이중 인덱싱을 하나의 인덱스로 줄일 수 있습니다. 다만 모든 원소를 처리하므로 시간 복잡도는 O(N²)로 같습니다.
- **더 큰 규모의 처리:** 현재보다 훨씬 큰 행렬이나 반복 작업에서는 병렬 처리 또는 전용 가속기 사용을 고려할 수 있습니다.

## CPU와 NPU

CPU는 운영체제와 다양한 프로그램을 처리하는 범용 프로세서이며 여러 코어와 벡터 명령을 이용한 병렬 처리도 가능합니다. 현재 프로그램은 Python 반복문으로 한 위치씩 처리하므로 CPU의 병렬 연산 능력을 직접 활용하지는 않습니다.

NPU는 같은 형태의 MAC을 대량으로 병렬 처리하는 데 특화된 장치입니다. 따라서 큰 행렬이나 많은 입력을 반복 처리할 때 장점이 있을 수 있지만, 실제 성능 차이는 하드웨어와 입력 크기에 따라 달라 별도 측정이 필요합니다.
